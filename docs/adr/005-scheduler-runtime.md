# ADR-005 · 调度跑在哪、崩了怎么出报

- **状态**: 已接受
- **日期**: 2026-08-25
- **背景**: Lab 6。系统要从「手动 collect」变成「持续撒网 + 早晚收网」。必须先定运行时和失败策略,否则调度器只是把不稳定放大。

## 决策

1. **调度器选 APScheduler,挂在 `uv run main.py serve`。** `main.py` 的 `collect` / `enrich` / `render --edition` 保持可单独调用。常驻进程与人手调试走同一条路,不用等到明天早上才能复现 bug。
2. **主力运行时放家里的机器(树莓派 / 旧笔记本 / NAS),不放 GitHub Actions,也不把云主机当采集面。** 决定性因素是 IP:住宅 IP 在平台风控里的信任度远高于机房 IP 和 Actions 公开网段。Cookie / 登录态也能长期放本地磁盘。
3. **出报策略是超时熔断 + 残缺出报。** 单版失败写「本栏目今日无数据」,报头列出失败版面,体检页印在最后。只有全部内容版面都失败且体检也写不出来时才算出报失败。
4. **GitHub Actions 若要用,只做心跳,不做爬虫。** 例如 6 小时没收到「出报成功」就发告警。不在 Actions 里跑 RSSHub/热榜。

## 明确不做

- 不为了「看起来高可用」把采集迁到云上。
- 不无限重试到 10 点才推早报。
- 不因一张网(RSSHub 容器被 kill)而跳过整期报纸。
- 不在本 Lab 做 Docker 全家桶与邮件推送(Lab 9)。

## 后果

- **正面**: 采集环境更像普通人上网;手动命令与 cron 行为一致;每天读报等于巡检。
- **负面**: 家里断电/断网时出报中断,需要以后用云端「只推送」或 Actions 心跳来补通知。笔记本合盖仍可能漏 tick,靠 `coalesce=True` 只补一次、不能补回错过的热榜快照密度。
- **成本**: 电费和机器是一次性的;云主机按月,且要用代理/住宅 IP 才能接近同等采集成功率。

## 何时重新评估

1. 有固定在线的家庭 NAS / 树莓派之后,把 `serve` 从开发笔记本迁过去。
2. 若需要「采集在家、LLM/渲染在云」,再拆成两段同步,不先把 SQLite 和 Cookie 送上公网。
3. 平台全面改用官方 API 且不风控机房 IP → 可以重新考虑云采集。
